# Установка обновления и откат

Обновление добавляет таблицы и индексы, включает SQLite WAL и busy_timeout. Старые subscriptions/settings/seen/members/invites/notifications сохраняются. Профиль браузера и токен используются прежние. Файлы `-wal` и `-shm` нельзя удалять у работающего SQLite.

## Перед установкой

Остановить прежний экземпляр через его окно или `uv run avito-service stop`. Запустить `uv sync --frozen` и `uv run pytest -q`. Для ручного запуска предварительно создать согласованную копию через SQLite backup API; обычное копирование одного файла у работающей WAL-базы недостаточно.

На macOS `uv run avito-service install` выполняет повторную установку в таком порядке:

1. Получает отдельную межпроцессную `data/deployment.lock` и удерживает её до завершения всей операции. Ожидание — до 25 секунд. При неудаче ещё не вызывается bootout, работающая служба не затрагивается.
2. Останавливает зарегистрированный LaunchAgent и подтверждает его отсутствие. На bootout и ожидание выгрузки отведено суммарно до 25 секунд. Ненулевой код print сам по себе не означает отсутствие: нужны известный код и диагностическое сообщение именно о нужном задании. Системные ошибки прекращают установку.
3. Дожидается освобождения `bot.lock` до 25 секунд и удерживает её во время резервного копирования SQLite и подготовки plist. Само приложение продолжает использовать прежнюю блокировку единственного экземпляра.
4. Создаёт согласованную копию через SQLite backup API и проверяет integrity_check. Копия хранится в `data/backups/`; прежние копии, база, профиль и настройки не удаляются.
5. Подготавливает plist и освобождает `bot.lock` для нового приложения. `deployment.lock` остаётся удержанной.
6. Выполняет bootstrap и до 30 секунд проверяет регистрацию, работающий supervisor и свежую строку Application ready с PID приложения. Дополнительно проверяется, что этот PID работает и является дочерним процессом supervisor. Старые строки журнала и строки другого процесса не подтверждают готовность.
7. Атомарно обновляет `deployment.json` с подтверждённым статусом и освобождает блокировку развёртывания. При ошибке сохраняет прежний manifest; последняя неудачная попытка записывается отдельно в `deployment-attempt.json`.

У всех subprocess есть таймаут. Обычно он составляет не более 5 секунд; для bootout используется оставшийся общий бюджет выгрузки. Опросы print и ps ограничены оставшимся временем своего этапа. Содержимое print является диагностическим форматом launchctl: если поля изменятся и готовность нельзя подтвердить, установщик не подставляет успешный статус.

Статусы и коды выхода install:

| Статус | Условие | Код выхода |
|---|---|---:|
| ready | Задание зарегистрировано, процессы живы, свежая готовность нужного дочернего приложения подтверждена | 0 |
| registered | Задание и процесс работают, но готовность приложения не подтверждена в срок | 2 |
| failed | Ошибка команды, таймаут или отсутствие зарегистрированного работающего процесса | 1 |

`ready` подтверждает запуск компонентов, а не доступность Авито или успешность каждой будущей отправки Telegram. WAITING_FOR_USER из-за 403/429 не является ошибкой развёртывания. Актуальную работу Telegram и очередь проверять через /health; сетевые ошибки не обходятся установщиком.

Для проверки готовности используется PID в новой строке журнала Application ready. Если запускается более старая версия без этого поля, установка может подтвердить только registered. Команда status показывает текущее состояние задания launchd и не заменяет полную проверку готовности.

## Проверка после установки

1. Проверить `status` в `data/deployment.json`: ready означает подтверждённый запуск, registered требует дополнительной диагностики. `uv run avito-service status` показывает текущее состояние службы. `data/bot.log` содержит Application ready и состояние источника. Отдельно проверить Telegram polling и отсутствие конфликтов второго экземпляра.
2. В Telegram открыть `/health`: очередь видна, статус и причина ограничения соответствуют журналу. При `VERIFICATION_REQUIRED`/`ACCESS_DENIED` автоматических повторов нет; при `RATE_LIMITED` следующая проверка идёт только после срока.
3. Сверить количество старых подписок, участников, settings и seen с резервной копией. Новые объявления могут увеличить seen после старта; уменьшения и удаления старых записей не ожидаются, кроме штатной очистки seen старше 30 дней.
4. При доступной выдаче дождаться одного обычного цикла. Если Авито просит проверку, владелец проходит её в окне Chrome бота (при необходимости после /unblock); бот сам продолжит сбор. Капча автоматически не решается.
5. Непрерывность и задержку оценивать после достаточного времени наблюдения. Развёртывание не является доказательством суточной устойчивости.

## Откат

1. `uv run avito-service stop` и убедиться, что процесс приложения завершился.
2. Создать новую согласованную backup-копию текущей БД, включая незавершённый outbox. **Не восстанавливать старую копию поверх новой автоматически**: иначе будут потеряны задания после обновления.
3. Вернуться к исходному коммиту `add11854a670ffbb95b7fcbe2592b0ee5f9db8cc` в отдельной ветке/checkout и выполнить `uv sync --frozen`. Новые таблицы старому коду не мешают. Если запускать старый код с новой базой, учесть: старая версия не отправляет outbox и может потерять новые уведомления при сбоях. Для надёжной доставки сначала завершить очередь новой версией либо сохранить её для последующего восстановления.
4. Старую версию запускать её штатным способом; команды avito-service в исходном коммите нет. Автозапуск LaunchAgent до обратного обновления отключить командой `launchctl bootout gui/$(id -u)/local.avito-monitor`.

Для восстановления повреждённой БД использовать проверенную backup-копию только после остановки всех экземпляров. Сохранить исходную повреждённую базу и её WAL рядом для расследования и извлечения заданий.

## Одновременные запуски и завершение

Приложение и отдельный avito-unblock используют один OS lock. Второй экземпляр прекращает запуск с кодом 78. Telegram, источник и worker завершаются с отменой asyncio-задач и закрытием сетевых клиентов/SQLite. После неожиданного падения незавершённые lease возвращаются в retry по истечении 120 секунд. После подтверждённого sent повторной отправки нет.

Развёртывания и команда avito-service stop сериализованы через deployment.lock. Неудачный конкурентный установщик не вызывает bootout. Ошибки на любом этапе освобождают блокировки; установка не убивает процессы по совпадению имени.
